# Улучшение помощника Velora — 2026-10-06

План согласован пользователем в чате. Реализация и проверки выполнены локально:
без деплоя и обращения к production-БД. Коммит и push разрешены последующим
отдельным запросом пользователя. Ранее изменённые файлы и документы сохраняются.

## Поведение

- Приветствия, благодарности, знакомство и простой small talk отвечаются без Gemini.
  Помощник представляет Velora и предлагает помощь с выбором. Посторонние задачи
  получают короткое дружелюбное перенаправление; вопросы об уходе разрешены.
- Читается весь доступный каталог прототипа. Популярность не ограничивает выборку
  первыми 12 товарами. Используются названия, краткие и полные описания, категории,
  теги и атрибуты. Пустые AI-поля не означают непригодность товара.
- Классификатор получает реальные slug и словарь имеющихся скалярных атрибутов.
  Неизвестные значения фиксируются в диагностике; потребность остаётся в тексте
  запроса для семантического подбора. Предположенная категория — мягкий сигнал.
- Доступность, активность, архив категории, зарезервированный остаток и бюджет
  проверяются сервером. Цена/категория не снимаются при неудачном поиске.
  Если соответствие не подтверждено, ответ уточняет условия вместо утверждения
  об отсутствии во всём магазине. Автоматические товары сверх бюджета не выдаются;
  покупателю предлагается уточнить запрос или изменить бюджет.
- Вместо трёх запросов Gemini используются классификация и объединённый подбор
  с ответом. В истории передаются упорядоченные ID карточек; сведения о них снова
  читаются из БД. «Второй», «его цена», «дешевле» используют актуальные записи.
- Обычный ответ ограничен запрошенным числом товаров; неизвестные ID, лишние
  товары и неподтверждённые цены не показываются как успешный ответ модели.
- При сбое модели допускается только буквальный поиск по каталогу с явным
  предупреждением, что пригодность не оценена. При отсутствии такого совпадения
  возвращается 503. Популярные товары всего магазина не подставляются.
- Ошибка восстанавливает текст запроса; повтор использует исходную историю и
  ту же строку пользователя. Неуспешные строки не становятся контекстом следующих
  сообщений. История ограничена числом записей и размером UTF-8.

## Диагностика и совместимость

Миграция `011_assistant_diagnostics.mts` добавляет JSONB `diagnostics` без изменения
товаров. Сохраняются этап, длительности, применённые/проигнорированные фильтры,
число каталожных записей, классификатор, кандидаты и причина сбоя даже при ошибке
финального ответа. Различаются ключ, модель, квота, timeout, сеть, формат и БД.
Тела ошибок провайдера не логируются; только фиксированные безопасные метки.
Секреты, cookies и CSRF не входят в диагностику. CSRF, CORS, сессии, схемы,
ownership и rate limit сохранены. Расширения истории и ответа обратно совместимы
со старым клиентом. Миграцию потребуется применить при отдельном согласованном деплое.
При публикации сначала обновить backend с миграцией, затем frontend: старый
backend со строгой схемой истории не принимает новое поле `productIds`.

Текущая реализация предназначена для небольшого каталога (50 товаров). При росте
выше 2000 доступных записей сервер явно откажет в подборе вместо скрытого обрезания;
для большого магазина потребуется отдельный индекс релевантности.

## Проверки

Регрессии выполняются исключительно в одноразовой PostgreSQL из `npm test`,
Gemini заменён тестовым провайдером. Проверяются Garnier ниже первых 12 с пустыми
AI-полями, известные и неизвестные фильтры, бюджет/остаток/категория, no-match,
количество товаров, контекст карточек, ошибки провайдера и БД, CSRF и rate limit.
Сборки frontend/backend, TypeScript, lint и desktop/mobile проверяются отдельно.
Это подтверждает логику и интеграцию; качество реального ответа Gemini и настройки
Render после будущего деплоя требуют отдельной production-проверки.

Результаты: весь `npm test` — 51/51; финальный повтор целевых тестов после
уточнения JSON-схемы — 24/24 проверок помощника. `npm run build`,
`npm run build:server`, `npm run lint` проходят. Lint сообщает существующие
предупреждения в старых файлах `output/playwright`; Vite сообщает размер JS-chunk.
`npx tsc -p tsconfig.app.json` обнаруживает существующую ошибку TS2345 в
`src/storefront/routing/AppRoutes.tsx:115` (unknown[] для availableBrands).
Эта строка совпадает с HEAD и не изменялась в работе над помощником.
Механическая проверка UI отмечает только существующий Roboto, который сохранён
по утверждённому дизайн-заданию.

В браузере проверены главная, каталог, категория, товар, избранное, переход
к корзине гостя (на вход), about/delivery/payment/contacts и виджет на них.
Desktop 1440×1000, mobile 390×844 и уменьшенный viewport 390×500: приветствие,
ожидание, карточка/переход, ошибка, восстановление текста и повтор без дубликата.
UI: 9 локальных POST (включая один перехваченный браузером ответ 503),
успешные запросы — 200, тест сбоя — 503, оба повтора — 200; JS-исключений нет.
Семантический ответ на стенде задаёт тестовый провайдер и не является проверкой
качества Gemini. Нельзя считать демонстрационный Cloud Cleanser подходящим
для сухого волосся: он выбран заглушкой исключительно для проверки карточки.
Garnier проверен отдельной регрессией на изолированных записях PostgreSQL.
Production-сообщений в ходе реализации не отправлялось; в предшествующем аудите
было отправлено ровно 3. Production-БД, конфигурация Render и деплой не менялись.

Воспроизводимость: `npm test -- --assistant-only` для помощника;
`npm test -- --assistant-preview` поднимает временный стенд на 4000 после всех
тестов. Vite запускается с пустым `VITE_API_ORIGIN`, чтобы использовать локальный
proxy. Callback `server/test/assistant.browser.mjs` запускается Playwright CLI
через `run-code --filename` против локального 5173. Для завершения стенда создать
`output/assistant-preview.stop`: runner закроет сервер и удалит свой контейнер.

Официальный контракт structured output сверялся с
[Gemini structured output](https://ai.google.dev/gemini-api/docs/structured-output)
и [GenerationConfig](https://ai.google.dev/api/generate-content#v1beta.GenerationConfig).
Схема генерируется из Zod; положительные integer ID преобразуются в inclusive
minimum, число элементов ограничивается запрошенным количеством и в Gemini-схеме,
и повторной серверной проверкой.
