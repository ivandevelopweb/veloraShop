# Velora: план реализации полнофункциональной админ-панели

> Предусловие: дизайн утверждён в `docs/superpowers/specs/2026-08-28-velora-admin-design.md`.
> Реализация начинается только после подтверждения этого плана.

## 1. Зафиксировать основу и зависимости

- Проверить текущие клиентские и серверные точки входа, не затрагивая пользовательские изменения.
- Добавить только необходимые пакеты для PostgreSQL-миграций, безопасной загрузки файлов и Cloudinary.
- Дополнить `.env.example` не секретными именами переменных: администратора и Cloudinary; реальные значения остаются только в локальном `.env`.
- Обновить README: запуск, миграции, создание первого администратора и настройка Cloudinary.

**Готово, когда:** проект устанавливает зависимости без предупреждений, а документация не требует хранения секретов в репозитории.

## 2. Ввести управляемые миграции PostgreSQL

- Подключить `node-pg-migrate` и команды для применения, отката и создания миграций.
- Сформировать начальную миграцию, совместимую с существующей схемой: роли пользователей, категории, расширенные поля товара, галерея изображений, позиции заказа и журнал действий администратора.
- Добавить индексы, внешние ключи, ограничения статусов и уникальности slug.
- Сохранить тестовый каталог из 50 товаров и привести его к новой модели без ручной правки базы.

**Готово, когда:** новая пустая БД поднимается одной командой миграций, а повторное применение безопасно сообщает, что миграции уже выполнены.

## 3. Реализовать роли и создание первого администратора

- Добавить роль `customer` / `admin` в модель пользователя и безопасно пробрасывать только нужные данные в ответ профиля.
- Создать идемпотентный seed первого администратора из `ADMIN_EMAIL` и `ADMIN_PASSWORD`.
- Добавить серверный middleware `requireAdmin`, который запускается после `requireAuth`.
- Не изменять текущую модель HttpOnly-сессии и CSRF-защиты.

**Готово, когда:** обычный пользователь получает 403 для любого `/api/admin/*`, а администратор — доступ; пароль администратора не выводится в логи и не отправляется клиенту.

## 4. Создать защищённый media-пайплайн

- Добавить endpoint загрузки только для администратора.
- Принимать изображение из формы, ограничить размер до 10 МБ, число файлов, расширения и фактический MIME-тип.
- Передавать допустимые файлы в Cloudinary в изолированную папку Velora и сохранять public ID, URL, ширину, высоту и alt-текст в PostgreSQL.
- Реализовать безопасное удаление медиа при удалении изображения или товара; ошибки провайдера не должны ломать данные в БД.

**Готово, когда:** администратор может загрузить, переупорядочить и удалить изображения товара, а пользователь без роли admin не может вызвать upload endpoint.

## 5. Расширить API управления каталогом

- Реализовать постраничный список товаров, поиск, фильтры по статусу и категории для администратора.
- Добавить создание, редактирование, архивирование, восстановление и окончательное удаление товаров.
- Добавить CRUD категорий, включая проверку невозможности удалить используемую категорию без явного переназначения или архивации товаров.
- Все входные данные валидировать Zod-схемами; SQL — исключительно параметризованный; изменения журналировать в `admin_audit_log`.

**Готово, когда:** API возвращает предсказуемые валидационные ошибки, данные не могут быть изменены чужим пользователем, а магазин показывает только активные товары.

## 6. Усилить оформление заказа и управление статусами

- Сохранить текущую заглушку оплаты: никаких платёжных провайдеров, списаний и реквизитов.
- При создании заказа в транзакции проверять остаток, уменьшать stock, сохранять снимок названия и цены позиции.
- Ввести разрешённые переходы: `new → processing → shipped → completed`, с отменой до завершения.
- Добавить административное чтение заказов, фильтрацию, смену статуса и просмотр состава заказа.

**Готово, когда:** администратор видит реальные заказы и историю изменений, а запас товара не становится отрицательным при одновременных заказах.

## 7. Разделить клиент на витрину и админ-пространство

- Сохранить текущие премиальные витринные сценарии: каталог, поиск, фильтры, сортировку, избранное, корзину, аккаунт и mock checkout.
- Внедрить читаемую маршрутизацию и разнести крупные компоненты по страницам, UI-компонентам, API-клиенту и типам.
- Создать защищённый `/admin` с UX-проверкой роли; сервер остаётся единственным источником авторизации.
- Для неавторизованных вести на вход, для не-администраторов — в личный кабинет с понятным сообщением.

**Готово, когда:** код не свёрнут в одну строку, витрина и админ-панель используют единый визуальный язык, а прямой переход на admin-страницы обрабатывается корректно.

## 8. Собрать полноценные админские экраны

- **Дашборд:** ключевые показатели, последние заказы, низкие остатки и быстрые действия.
- **Товары:** таблица/список с поиском, фильтрами, пагинацией, статусами и архивом.
- **Форма товара:** название, slug, описание, цены, остаток, категория, статус, alt-тексты, drag-and-drop порядок изображений, предпросмотр и понятные состояния загрузки.
- **Категории:** создание, переименование, отображение количества товаров и безопасное архивирование/удаление.
- **Заказы:** таблица, фильтры, карточка заказа, состав, сумма, покупатель и контролируемое изменение статуса.

**Готово, когда:** администратор может самостоятельно вести каталог и заказы без правки БД или исходного кода.

## 9. Доработать витрину под управляемые данные

- Перевести каталог и карточку товара с фиксированных данных на API, сохранив 50 тестовых товаров.
- Поддержать несколько изображений, главное фото, отсутствие изображения, остаток, цены и статус доступности.
- Показывать понятные пустые и ошибочные состояния, не ломая навигацию и корзину.

**Готово, когда:** изменённый или добавленный в админке товар корректно отображается в витрине без редактирования frontend-кода.

## 10. Проверить безопасность и надёжность

- Выполнить проверку TypeScript/Node-кода по secure-by-default практикам.
- Проверить цепочки: CSRF для cookie-мутаторов, CORS allowlist, Helmet, rate limit авторизации, owner/role checks, валидация и upload limits.
- Убедиться, что клиент не получает токенов сессии, Cloudinary secret, пароль или служебную ошибку PostgreSQL.
- Ручными сценариями проверить запреты на admin API для гостя и customer, некорректные файлы и невалидные статусы заказа.

**Готово, когда:** все критические маршруты имеют авторизационную и валидационную защиту, а обнаруженные проблемы исправлены до передачи результата.

## 11. Финальная проверка и передача

- Запустить миграции на чистой базе и seed администратора.
- Проверить ключевые desktop и mobile сценарии: регистрация, вход, корзина, заказ, доступ к админке, добавление товара с изображением, редактирование, архивирование, заказы.
- Выполнить `npm run build`, серверную сборку, линтер, форматирование и аудит production-зависимостей.
- Обновить README с точными командами запуска, миграций, seed и переменными Cloudinary.

**Готово, когда:** проект запускается по документации, проходит сборку и демонстрирует законченный безопасный full-stack кейс для портфолио.

## Порядок внедрения

Этапы выполняются строго в порядке 1 → 11. После этапов 2, 4, 6 и 8 проводятся локальные проверки до перехода к следующему этапу. Реальные ключи Cloudinary потребуются только для проверки фактической загрузки изображений: интерфейс и серверная конфигурация смогут быть собраны заранее.
